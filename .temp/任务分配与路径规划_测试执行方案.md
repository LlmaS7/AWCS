# AWCS 任务分配与路径规划测试执行方案

**文档状态：仅方案，尚未执行测试。**  
编制日期：2026-10-19。适用于 AWCS 当前源码，执行前必须重新核对接口和代码版本。

## 1. 给执行 AI 的任务说明

本方案用于对任务分配、路径规划及二者协作进行可复现验证，形成可供竞赛材料引用的证据。当前仅要求编写方案；收到后续明确的执行指令后，再按本方案创建测试脚本并运行。

执行时遵循以下约定：

1. 先读项目约定与最新源码；保留已有未提交修改，记录工作区状态和源码哈希，不能只用 Git 提交号标识被测版本。
2. 测试代码、生成地图、日志和结果统一放在项目 `.temp/testing/`；本方案保留在 `.temp/` 根下。使用独立运行目录，不覆盖旧结果。
3. 默认只新增测试与报告，不修改生产算法、正式地图、个人地图库、运行记录或配置。发现问题先保留最小反例与定位，不能为了通过而放宽断言、删用例或调整生产规则。
4. 优先使用现有 `.venv` 和 Python 标准库 `unittest`、`itertools`、`random`、`subprocess`；不接入模型服务，不读取密钥，不依赖图形窗口和外部网络。
5. 先完成独立校验器及小规模对照，再扩大到地图集。独立校验器不能调用被测匹配器、路径搜索器或生产冲突检查函数作为自己的判据。
6. 默认串行执行，避免多个求解器争抢 CPU 使时间预算失真。子进程设硬超时；只停止本轮创建的进程。
7. 运行完提交：结果汇总、原始数据、失败反例、重现命令、可用于视频的案例，以及尚不能下结论的范围。

本测试的目标是提供“在明确版本、输入与预算下的正确性和安全性证据”。有限测试不能证明任意地图、无限任务流永远没有问题。

项目位置：`E:\_PROJECTS\AWCS`。

## 3. 通过、失败和未完成的分类

每个用例必须有一个最终状态：

| 状态 | 定义 |
| --- | --- |
| `PASS` | 该用例全部预设断言满足，并完成规定检查 |
| `FAIL` | 出现目标错误、违规归属、非法路线、错误状态转换，或违反用例明确要求的拒绝行为 |
| `INCONCLUSIVE` | 超时、规划预算不足、运行步数耗尽或资源限制，无法完成本用例的结论 |
| `BLOCKED` | 环境或依赖缺失，无法开始验证 |
| `NOT_RUN` | 尚未执行，包括总预算到达而剩余未调度的用例 |

对“应拒绝非法路线”的用例，按预期拒绝且状态保持正确可以 `PASS`。对“应完成搬运”的用例，安全暂停只证明保护机制有效，整体完成性仍是 `INCONCLUSIVE`，不能计为完成通过。

记录分开的子结论：`assignment_correct`、`path_safe`、`tasks_completed`、`failure_handled_safely`。不能只看退出码或一个总的 passed 字段。

特别注意：`collisions == 0` 不能单独证明路线安全。生产代码可能在执行前拦截非法方案；必须核对规划输出、拒绝事件和实际位置序列。

## 5. P0：建立可信的独立判据

### 5.1 执行环境与版本

记录：时间、Python 版本与路径、操作系统、CPU/内存、当前工作目录、Git 提交、工作区差异清单、源文件 SHA-256、测试脚本 SHA-256。对涉及的源码在运行后再校验一次；若运行中发生变更，拆分批次或重新运行受影响用例。

输出目录使用唯一批次名。测试脚本设置项目根目录的导入路径，但不修改生产配置中的 `OUTPUTS`，也不调用会覆盖 `outputs/last_*` 的保存入口。

Windows 使用进程生成时，把入口放进 `if __name__ == '__main__':`。单个用例由专属子进程执行，超时后保存输出并清理该子进程及由它创建的规划进程。

### 5.2 独立轨迹检查器

输入为冻结后的实际网格、机器人初始位置、每台路线、业务事件与逐步状态。自行实现以下检查，不导入生产 `first_conflict`、`validate_paths`、`validate_itineraries` 或 `assert_invariants` 来代替判断：

1. 每台机器人路线非空，首格等于规划时的真实位置，所有坐标在网格内且为可通行格。
2. 每一步只能等待或移动到上下左右相邻格，曼哈顿距离不得超过 1。
3. 任意时刻不同机器人位置不同。
4. 任意一步不能出现两机器人交换各自上一时刻位置。
5. 短路线在尾部按最后位置补齐，检查到最长路线末尾；最终停车位置互不冲突，并结合给定预约检查停车持续占用。
6. 按作业点顺序检查取货、连续装货、配送、连续卸货与停车。若在时刻 s 到达且 hold=h，则至少在 s～s+h 连续停留，不能中途离开后回来凑次数。
7. 实际执行中任务不得同时属于两台机器人；已载货任务不得迁移给另一台；实际装卸发生前不能凭规划结果标记完成。
8. 对滚动模式只检查已认证窗口和执行前缀的相应承诺，不能把局部路径当作已完成所有取送作业。

同时记录并比较生产校验器结果，生产检查通过而独立检查失败即为关键缺陷。

### 5.3 先检查判据本身

给独立检查器输入人工构造的正常路径，以及分别包含同格冲突、对向换位、穿墙、跳格、终点占用冲突、提前结束装卸、重复任务归属的错误样本。必须全部识别对应错误。

为这些人工样本画出 2～4 个时间步的状态表，人工核对预期；不能仅用生产规划器生成的“正常样本”证明独立检查器正确。

## 6. P1：任务分配算法的正确性对照

### 6.1 独立穷举基准

测试 `match` 时使用 `Slot`、`Task` 或满足相同字段要求的轻量对象，直接提供预先生成的代价表。

独立基准枚举每个机器人“不分配”或“选择一项未被选择的可行任务”，自行累计并按 Python 元组字典序比较：

```text
(-5级分配数, -4级分配数, -3级分配数, -2级分配数, -1级分配数,
 [偏好惩罚之和，仅在启用偏好时加入], ETA之和, created_at之和)
```

约定 `None` 或 ETA≥1,000,000 的边不可用，与当前 `match` 契约一致。基准不调用 `match`、`minimum_assignment`、权重编码或旧版匹配器。

比较最优目标元组，并独立重算返回 pairs 的目标值；存在同分方案时不要求机器人—任务组合逐项相同。旧版 `legacy_matching` 可作第三方位的项目内交叉检查，但不能作为唯一判据。

### 6.2 必测固定用例

| ID | 输入设计 | 验收点 |
| --- | --- | --- |
| A01 | 无机器人、无任务、任一侧为空 | 返回空匹配与正确维度的零分数 |
| A02 | 任务多于机器人／少于机器人／全部不可行 | 不重复分配，空分配合法，不选择禁用边 |
| A03 | 同等级代价矩阵 [[1,2],[3,100]] | 选择总代价 5 的整体匹配，不能得到 101 |
| A04 | 一台机器人面对远距离 5 级与近距离低级任务 | 高等级目标不被距离优势覆盖 |
| A05 | 等级、可行数量相同，软偏好与较低 ETA 冲突 | 按定义先比较可满足的偏好，再比较 ETA |
| A06 | 相同等级、偏好和 ETA，不同创建时刻 | 比较创建时刻总和；不要误要求逐任务严格 FIFO |
| A07 | 某任务仅允许指定机器人执行 | 不可被其他机器人接走；不可用时等待 |
| A08 | 代价 0、999,999、1,000,000、None，以及较大的创建时刻 | 边界和禁用值行为正确，无固定权重压制失效 |
| A09 | 所有目标同分，多组等价匹配 | 结果可不同，目标值与唯一归属仍正确 |
| A10 | 输入重排，保持 ID 与代价关系不变 | 最优目标元组不变；不强求同分 pairs 完全相同 |

再随机生成：机器人数量 0～4、任务数量 0～5 的 30 种组合，每种 40 个固定种子，共 1,200 例。混合优先级、不可行边、不同 ETA、创建时刻和有无偏好，每例与独立穷举比较。随机种子清单在运行前写入 manifest。

### 6.3 匈牙利实现的独立检查

对小型非负整数矩形矩阵，用列排列穷举比较 `minimum_assignment` 总代价；包括零行、单行、方阵、列多于行、同代价、大整数与非法矩阵形状。非法输入以函数当前明确契约为准，不臆造未承诺的处理方式。

对 `completion_cost` 另外用人工可数距离的微型网格验算：释放时间、取货距离、装货、配送距离、卸货均被计入。静态最短距离使用测试侧 BFS 复核。

## 7. P2：业务分配与装卸约束

用合法固定小地图和 `Simulation(initial_tasks=0, map_definition=..., robot_count=...)` 创建场景，再用公开业务方法添加和调整任务。优先通过真实执行推进到目标阶段；必要的构造状态必须独立核对，避免夹具本身不一致。

| ID | 场景 | 必须检查 |
| --- | --- | --- |
| B01 | 空闲机器人接普通任务 | task 与 robot 双向归属一致、唯一且地点正确 |
| B02 | 普通任务尚在 to_pickup，插入紧急任务 | 仅在规则允许时抢占，被释放任务保留并回到待处理状态 |
| B03 | picking／to_delivery／unloading 时插入紧急任务 | 不迁移货物、不打断装卸，可预约下一任务 |
| B04 | 同时存在多项紧急任务和忙碌机器人 | 两阶段分配、延迟槽位 release 与预约归属正确 |
| B05 | 人工指定空闲机器人／锁定当前执行者 | 指定关系正确，未绕过更高等级任务 |
| B06 | 指定给忙于其他任务或已载货的机器人 | 按契约拒绝，无附带取消或改派其他任务 |
| B07 | 偏好机器人可接手／忙碌 | 前者优先满足；后者允许其他机器人，硬优先级仍先行 |
| B08 | 解除指定／软偏好 | 恢复自动模式，不取消任务、不保留残余请求机器人 |
| B09 | 装货前取消／开始装货后取消 | 前者释放归属，后者拒绝；无重复完成或丢失货物 |
| B10 | 重复 dispatch，无新增输入 | 不产生重复归属，不改变已有载货与连续服务事实 |

验证紧急第一阶段与剩余任务第二阶段的局部目标。不能用“一次性全任务联合最优”去断言实际两阶段调度错误。

## 8. P3：路径规划的独立验证

### 8.1 预约表边界

用有限 horizon=12，把独立位置占用逐时间步展开成集合，对照 `safe_intervals` 的补集；分别检查：空占用、t=0、末时刻、单点闭区间、相邻区间合并、重叠区间、全覆盖、持续终点。

对 `add_path` 同时检查顶点表和禁行边表：A→B 的已规划移动应禁止另一机器人同一步 B→A。单格不动路线也必须持续占位。修改占用后安全区间缓存必须失效；clone 的修改不能污染原预约表。

### 8.2 单机器人 SIPP 与朴素时空基准

实现小网格上的独立逐时间步搜索：状态至少包含位置、时刻、下一作业点、剩余连续服务时间和已完成交付代价。使用显式顶点与边占用集合，不调用生产预约表来构造基准可行性，不调用生产启发式或状态归一化函数。

先在“单终点、无服务”的子集中使用 BFS 验证最早到达；多作业点子集使用有限时间展开的动态规划或保留必要非支配代价的搜索，比较约定字典序代价，不能只保留最早到达而丢掉已完成交付的代价差异。

基准范围建议：3×3～6×6、horizon 12～24、1～3 个作业点，至少 200 个固定种子实例。障碍、预约、hold 和终点检查采用独立数据源生成；确保基准在有限状态空间内完整搜索。

固定用例至少覆盖：

- 直线到达、绕障碍、需要等待到安全区间开放。
- 目标格可用但反向边在该时刻禁行。
- 原位置无法安全等到目标开放，必须寻找其他路线或返回失败。
- 到作业点后剩余安全时间不足以连续装卸。
- 起点 t=0 被占用；停车点会在之后被他人持续占用。
- 目标只在 horizon 之后可达；按有限窗口结果处理，不说全局无解。

对基准可行的简单固定用例要求规划成功且路线安全。对随机例，分别记录“基准可行但生产未求得”“代价不一致”“生产成功但不安全”，不要把三类问题混为一谈。SIPP 子问题若主张代价正确，需对该有限模型完成相应对照；不能将整个多机器人启发式协调器视为全局最优算法。

### 8.3 小型多机器人联合状态对照

对 2～3 台机器人、最多 5×5 小地图、horizon 8～12、固定不同停车终点，实现独立联合状态 BFS：每台每步选择等待或合法邻格，过滤同格与对向换位；已完成终点的机器人按夹具约定保持占位。先不含装卸，再单独加一个可人工核对的 hold 场景。

固定夹具至少包含十字路口、带避让位的单通道、必须绕行的环路、停车堵路，以及有限 horizon 内不可行的实例。

联合基准用于提供小场景的可行性证据；不要求启发式规划器在所有可行随机图上都能找到解。若生产报告 success，则必须通过独立检查；若超时而基准可行，记求解覆盖不足。有限 horizon 的基准失败不是任意时间范围内无解的证明。

### 8.4 反向测试：故意提交非法计划

构造带成功标记、但路径含冲突、穿墙、跳步、打断装卸或更改载货归属的 Proposal，分别交给 `apply_proposal` 或实际执行保护入口。检查拒绝、暂停与异常契约，并比较调用前后的业务输入与物理状态。

验收重点是“非法计划不能推进时间并导致危险移动”，不统一要求所有接口采用同一种异常形式。修改 tick、完成时间、等级或货物归属的伪造计划也不得被接受。

## 9. P4：借助地图生成器建立集成测试集

### 9.1 使用方式

优先直接导入纯生成函数，无需启动浏览器服务。当前接口是：

```python
from map_studio.generator import generate

definition = generate(
    width=96, height=64, robots=32, seed=20261018,
    shape='l', aisle=3, density=65, obstacles=20,
)
```

这段仅展示执行时使用的接口，不代表现在已运行。输出只保存到 `.temp/testing/datasets/maps/`，不调用 publish，不写正式 `maps/` 或个人 `map_studio/library/`。

`robots` 是生成地图的容量，实际仿真数量另行传给 `Simulation`。

### 9.2 冻结地图矩阵

主集生成：

| 参数 | 固定取值 |
| --- | --- |
| shape | rectangle、l、t、u、courtyard、rooms、random |
| width / height | 96 / 64 |
| robots 容量 | 32 |
| aisle / density / obstacles | 3 / 65 / 20 |
| 地图种子 | 20261018、20261019 |

共 14 个地图快照。每张图以相同参数重复生成两次，比较规范化 JSON 哈希，并检查生成器版本与 metadata。通过正式 `validate_map` 与独立四邻域 BFS 检查通行区、作业点、容量与起点前缀连通。

若某个合法范围内的组合被生成器拒绝，保存参数、异常和原因；将生成契约问题与“地图成功生成但校验失败”分开报告。不能悄悄换种子或地图，把 14 张的原定矩阵变成筛选后的成功样本。

另对内置 9 张地图做静态检查，以及生成器尺寸、容量、aisle、density、obstacles 的上下界和越界拒绝测试。地图有效不等于多机器人任务必然可解。

### 9.3 28 个主集搬运用例

每张生成图分别跑 4 台、16 台，共 28 个用例。使用：

- 模式 `scalable_full`、coupling=`off`、单次规划预算 3 秒。
- 每例初始任务 `2 × 机器人数量`，等级覆盖 1～5，显式固定任务清单；关闭自动无限下单。
- 任务随机数使用测试侧独立 `Random`；任务种子为地图种子 + 1000，清单预生成并写入 manifest。
- 有限上限：6,000 个仿真时间步、每例子进程硬超时 90 秒；任一达到即保存现场并分类。
- 至少追踪所有任务完成；可继续有限推进，记录机器人是否完成停车，不把任务完成与全部停车混成一个结论。

初始使用 `Simulation(initial_tasks=0, map_definition=definition, robot_count=n, profile=PlanningProfile(...))`，再按清单添加任务。避免把随机默认初始任务混进预设工作负载。

每次规划后保存规划前起点、作业序列、返回路线和诊断，执行前用独立检查器复核；每个 tick 保存前后位置、阶段、载货与任务归属，持续检查安全和业务不变量。轨迹采用流式写入，不依赖生产系统有限长度的 frames 缓冲。

如果地图存在按种子追加的障碍，保存 `sim.warehouse.export_map()` 获得实际网格快照，记录其哈希；不能只保存名义地图 JSON。

### 9.4 有限动态任务流

另选 rectangle、courtyard、rooms 各一张，16 台，预先生成 60 项任务。在 tick 0、40、80、120、160 各注入 12 项，最后一次注入后停止，继续排空；上限 10,000 tick、120 秒。

若中途安全暂停而到不了后续注入时刻，剩余事件标为未触发，不能跳过失败现场后继续当作同一完整运行。记录队列长度、完成数、平均及 P95 周转、等待、距离、规划耗时。

有限批排空成功可支撑该输入下的持续调度表现，不能作为无限任务流稳定或无饥饿的证明。

### 9.5 复用地图工坊的试运行

`inspect_map(definition)` 可补充正式静态检查；`probe(definition, robots, seed)` 可补充一次工坊原有试运行，建议先对 2 张地图执行。

当前 probe 使用 `max(9, robots)` 个随机任务，规划预算对 32 台及以下为 3 秒、超过 32 台为 8 秒；有有限 tick 与外层墙钟限制。它复用生产检查，且结果可能为 `inconclusive`，因此不能替代独立轨迹检查或整个主集。

若需要硬超时或避免导入环境影响，可用专属子进程调用 `map_studio/bridge.py`，经 stdin 提交 JSON `{definition, probe, robots, seed}`；每次保存完整请求和响应，禁止覆盖旧报告。

## 10. P5：事件与失败恢复

| ID | 事件／故障 | 预期性质 |
| --- | --- | --- |
| F01 | 普通任务未装货时紧急插单 | 分配重新考虑，旧计划失效，安全与唯一归属保持 |
| F02 | 装卸过程中取消或改派 | 按业务规则拒绝，不提前结束服务 |
| F03 | 同一取货／配送点有多项任务 | 允许顺序使用，不允许同时占格 |
| F04 | 缩短规划预算导致未求得方案 | 任务保留、安全暂停、不宣称数学无解 |
| F05 | 相同场景恢复合理预算后重试 | 重试结果如实记录，无重复任务、错误完成或位置跳变 |
| F06 | 切图／重置后返回旧请求结果 | 旧结果不覆盖新场景；任务与位置保持新场景状态 |
| F07 | 同地图同 tick，但 domain_revision／request_id 已变化 | 过期结果拒绝，不能只比较地图与时间 |
| F08 | 规划进程返回异常／中断 | 不执行未经验证路线，结果与异常可追溯 |

超时保护优先用可控 fake worker／预设失败 Proposal 验证，不依赖“0.05 秒必定超时”等易受机器速度影响的假设。再对少数真实运行测量超时行为，并留出进程启动和清理开销。

异步过期结果使用最小控制器夹具和假 worker，不调用会启动 AI、读取本机设置或打开 UI 的构造流程；真实规划进程生命周期另做隔离烟测。执行 AI 应核对 Controller 当前字段与结果接收条件。

不要通过实际切换用户正在运行的仓库来完成测试。

## 11. P6：规模、联动与实验能力

### 11.1 32 台目标规模

对内置 `fleet_64x64`、`irregular_96x64` 和生成的 rectangle、rooms 各一张，使用两组固定任务种子，共 8 例。每例 64 项有限任务，预算 3 秒，最多 10,000 tick，子进程上限 120 秒。

若预算不足，可以追加 8 秒对照批次，但保留原始结果、明确不同预算，不能把对照结果覆盖成默认预算通过。

### 11.2 64 台实验规模

使用内置 `experimental_128x96`，以及 128×96、容量 64 的 rectangle 和 rooms 生成图，两组任务种子，共 6 例。每例 128 项任务，预算 8 秒，上限 15,000 tick／180 秒。

结果单独标为实验档，允许求解覆盖不足，但任何非法执行、任务丢失或错误成功标记仍是缺陷。不得以 64 台失败去掩盖 16 台主集结果，也不得用地图允许 64 台替代实际完成证据。

### 11.3 联动与滚动模式

- 对同一冻结地图、任务列表分别测 coupling=`off`、`estimated`、`candidate`；记录任务等级目标、偏好、路径代价、实际完成和耗时。不要求 candidate 对每次实测都更快或更优，因为时间预算可能限制候选搜索。
- 使用小规模可控夹具验证 candidate 不降低规定的优先级／偏好前缀，且仅从已校验可行候选中选取。
- 对 rolling 固定 window=32、execute=4，核对每次执行不超出认证前缀，到期重新规划，尾部等待符合停止证书；有限路径不等于所有任务完成。
- `legacy_full` 可作交叉比较，但它与默认模式共享部分项目代码，不能作为唯一正确性基准，也不能预设两者必须给出相同路线。

性能对照至少在同环境重复 3 次，串行运行，分别报告结果数量、中位数和范围；不把跳过或失败的运行剔除后再只报成功均值。

## 12. 汇总、验收与失败处理

### 12.1 每例记录字段

`case_id`、阶段、状态、源码哈希、地图参数和实际地图哈希、机器人数量、任务种子与完整任务清单、事件时间表、规划模式与预算、horizon/window、运行步数、墙钟耗时、完成／取消／剩余任务数、匹配 oracle 分数、独立安全检查结果、生产保护拒绝次数、规划状态分布、规划耗时 P50/P95、移动距离、等待、首次失败时刻、异常堆栈、重现命令与附件位置。

实际多机器人总代价与匹配阶段 ETA 分开记录。平均耗时、规划耗时、调度时间步使用明确单位；没有样本时记 null，不能用 0 冒充结果。

### 12.2 主测试验收门槛

1. 独立校验器的正常／错误样本自检全部通过。
2. 固定匹配例和 1,200 个随机小规模例全部与独立穷举目标一致，无非法边或重复归属。
3. 业务分配固定场景全部满足规则。
4. 预约表与有限范围 SIPP 对照无未解释的安全、代价或判定差异；简单可解固定夹具全部通过。
5. 28 个主集用例逐例给出结果，成功用例全部通过独立轨迹复核；要宣称“该主测试集全部通过”，必须 28 例均完成预定任务并满足全部断言。
6. 非法方案与过期结果均被阻止，且状态未被错误改变。
7. 主流程无 `FAIL`；仍有 `INCONCLUSIVE`、`BLOCKED`、`NOT_RUN` 时，不得宣称整个执行方案全部通过。

主集、32 台、64 台和滚动模式分开汇总。对被声明支持但无法完成的目标场景，即使全程安全，也必须如实说明完成性限制。

### 12.3 发现问题时的动作

先保存完整现场，再缩减机器人、任务和地图，得到最小可重现输入。保留首次失败版本与结果，记录期望、实际、首次违规 tick、调用链、状态前后差异。

通过重现区分：夹具／独立判据错误、生产功能缺陷、有限预算导致求解覆盖不足、环境阻塞。不能将所有规划失败归因于机器太慢。

若之后另行修复生产代码，使用新批次与新哈希，重新执行失败用例和受影响回归集。报告同时保留修复前反例及修复后结果。

## 13. 执行入口的约定

## 14. 面向竞赛视频的证据提炼

执行后建议挑选四类真实结果：

1. **匹配正确性**：展示固定贪心反例与穷举对照的实际统计，说明是在给定目标下验证。
2. **路径安全性**：展示一个共享通道或交叉口的逐步位置表，同时显示独立检查的冲突判定。
3. **业务规则**：展示紧急插单前后分配，以及载货／装卸不被中断的状态记录。
4. **地图泛化**：展示冻结的七类布局与逐例完成／未完成汇总，标注规模、任务数与预算。

可以在报告中使用如下模板，但必须以本次真实结果填入：

> 在源码快照【哈希】、【运行环境】和【预算】下，完成【N】个预设测试，其中【P】通过、【F】失败、【I】未得结论。小规模匹配与独立穷举对照【结果】；对【M】段返回路线及逐步轨迹进行了独立复核，发现【C】处违规。结论仅适用于该测试范围。

安全暂停、预算不足、未运行和实验档限制都应保留在完整报告中。视频可以精选案例，原始证据必须能够追溯到同一被测源码和地图快照。
