# AWCS Agent 能力测试执行方案

版本：**v2.0 · 2026-10-20 修订**。状态：**仅修订方案，不执行新测试、不调用 API、不读取 key.md 内容。**
适用项目：`E:\_PROJECTS\AWCS`。
目标：获得可重复、能定位失败原因、能区分模型能力与后端保护的测试证据。

旧测试的脚本与结果不作为本版已实现、已验收或已通过的依据；本版全部数量为未来计划。用户已要求清理旧 Agent 测试产物，执行本版时从新目录、新版本和空成绩表开始。任务分配/路径规划的既有测试资料另行保留。

## 0. 本版必须先落实的规则

1. **先验证测试系统，再消耗真实调用。** 完成 H01—H20 测试驱动自检与 O01—O40 保护检查。正确模型脚本应通过，具有可控错误的脚本应被相应判据检出；“给定答案能跑完”不足以证明判据有效。
2. **按依赖规定查询，不要求所有写操作具有相同工具序列。** 不存在任务的预期异常也属于真实查询证据；静态拒绝不强制查询；明确对象的原子 increment 可直接执行，再据回执解释。具体规则见 10.2。
3. **分别判定业务、协议、流程、回答和后端保护。** 每条结论带证据；不能把“没有错误副作用”当成“模型理解正确”，也不能把过程偏好当成业务错误。
4. **语义复核必须有可执行流程。** 默认允许执行 AI 按冻结 rubric 完成有证据的语义审阅，标明 reviewer_type，不伪称人工签字。无法判断的具体主张再进入人工队列，不把全部结构正确样本自动锁成未完成。
5. **文档核查必须到来源语义。** JSON 合法、ID 存在、来源块存在，只证明必要条件；还须检查该块真实支持取送地点、等级、次数、约束和排除理由。
6. **人工确认是独立步骤。** 预先规定可核对的 issues 和不得自动接受的约束；不能一遇非空 issues 就跳过全部确认，也不能为了继续而勾选忽略全部约束。
7. **闭环必须有匹配所声称能力的前提。** 验证紧急抢占需真实资源竞争，验证软偏好回退需偏好机器人确实忙碌；任务少而机器人多只能证明基本接入。
8. **原始记录不可覆盖，测试缺陷也不算模型错误。** 判据或夹具不合格记 TEST_INVALID，并保留原始断言；修正后的离线证据重算与新增真实调用分别编号，不拼接最好成绩。
9. **权限不足时交付可运行的外部入口。** 清楚说明哪些动作尚未完成；执行人员在自己终端运行。聊天中的“允许”不视为运行环境权限已改变。
10. **本版主矩阵仍为 60 × 3 = 180 段。** 另设 24 段独立挑战集，单独给分母；6 个闭环另计。不以参数子检查、摘要请求或协议探测凑会话数。

## 1. 执行任务、授权与范围

当前任务仅为完善方案。只有用户后续明确要求启动测试时，才实现或执行本版测试脚本、读取凭据并调用服务；不得把以前一次授权当成本次修订后自动重跑的指令。

测试回答六个问题：需求是否理解正确；是否使用当前真实地点和状态；工具及参数是否满足授权；程序是否阻止非法/重复/过期写入；解释是否符合回执；合法任务能否进入真实调度并完成搬运。

执行约定：

- 保留生产源码、正式地图、个人设置、已有算法测试及用户未提交改动。本方案不授权修复生产代码；发现问题先交付最小反例。
- 真实模型、离线预设响应、网络故障注入、人工确认和状态推进分别标注。只有真实被测模型产生的决策计入真实 Agent 能力。
- 主矩阵首次执行为正式成绩；不因失败换措辞、补提示、调参数、自动重试或删除样本。诊断和修复后版本另立记录。
- 预期来自冻结的业务事实和来源文档；不调用生产 normalize() 反推出标准答案，不把被测模型的自评分当判据。
- 不强求唯一工具序列或固定中文措辞；按业务等价性、查询依赖及真实副作用判定。
- 重点是任务级正确性和可靠性，不以动画、自然流畅的回答、HTTP 200 或进程退出码替代验收。
- 4/16 台机器人用于 Agent 接入验证，不能据此重写既有算法的规模、最优性或拥塞能力结论。

## 2. 凭据、运行环境与预算

### 2.1 凭据与真实配置

唯一指定凭据路径：`E:\_PROJECTS\AWCS\.temp\key.md`。
准备、修订、测试系统自检和离线保护阶段不读取该文件。网络预检开始前才在本地进程中解析 `base_url`、`api_key`、`model`；`effort`、`timeout` 可选并沿用生产校验。字段缺失/歧义仅输出字段名，禁止打印原文、候选密钥、配置快照或异常局部变量。

- 只使用明确绑定的服务与模型，不试发其他地址，不枚举其他付费模型。地址沿用生产 HTTPS 校验；HTTP 只供本机夹具。
- 不假定服务商或模型能力；支持 thinking、工具调用、流式完成标志等都由生产适配器的只读预检证明。HTTP 200 不等于工具参数或 JSON 结构有效。
- 不为通过预检改 effort、提示词、schema、tool_choice、输出上限、重试策略或适配器；不兼容则记录具体限制。修改后必须按新配置另立批次。
- 注入隔离 Configuration(path=本批配置, store=内存存储)，remember=False。密钥只在内存，不写入系统凭据库，不覆盖 local_settings.json，不经命令行、环境变量、模型输入、规划快照或子进程启动参数传递。
- 不保存 Authorization、HTTP headers、完整请求对象、reasoning_content、原始 SSE 全量文本。usage 中 reasoning_tokens 等计数可保留，不保留内部推理正文。
- prepare/offline 不依赖 Key 存在；report/review/export 不为生成报告强制再次读取 Key。脱敏自检使用合成 Key，产物采用白名单并在网络执行结束前完成敏感信息检查。

### 2.2 环境可执行性预检

先只读确认目标目录权限、Python 路径、已有依赖、规划子进程 spawn、精确本机回环地址/端口、配置隔离及报告写入。外网限制、本机端口限制、依赖缺失、生产协议不兼容分别报告，不统称“模型失败”。

若当前执行环境不能联网或不能在目标项目落盘，先完成可做的准备工作，给出已经自检的用户终端入口；未执行动作必须明确说明。测试脚本/产物使用一个固定可写根目录，manifest 中记录实际位置，不把产物散放到多个项目。不得绕过沙箱限制或声称聊天授权能解除限制。

### 2.3 默认预算与停止规则

| 项目 | 上限/规则 |
| --- | --- |
| 并发 | 一个被测模型请求、一个状态控制器；不同 case 不共享会话、账本、草稿 |
| 主矩阵 | 60 场景 × 3 次独立重复 = 180 段；12 个冒烟占其中 repeat_1 |
| 挑战集 | U01—U24，各 1 段，独立分母 24；完整范围声明必须报告是否执行 |
| 闭环 | X01—X06，各 1 段；主矩阵数据仅在前提与模型决策完全相同时引用 |
| 冒烟累计调用 | 协议预检和 12 例冒烟合计最多 60 次外部模型请求 |
| 整批外部模型调用 | 合计最多 1,200 次，包含被测、摘要、协议、失败、外部评审模型、诊断及新增闭环调用 |
| 单用户轮次 | 沿用生产 8 次模型请求、12 次工具调用；执行前重新核对源码 |
| 模型等待 | 沿用配置，默认 300 秒；不覆盖生产连接/读取超时；以单调时钟检测剩余时限 |
| 会话硬上限 | 900 秒，覆盖多轮、规划等待、证据收集与确认；到期不再提交新业务 |
| 整批执行时限 | 4 小时，从正式执行启动计算，跨阶段累计；准备与事后离线报告不耗本额度 |
| 闭环 | 每例最多 2,000 个实际仿真时间步、180 秒墙钟，先到为准；单次规划预算默认 3 秒 |
| 重试 | 正式首次计分不自动重试。诊断最多 1 次，单独目录与成绩，不覆盖首次结果 |

计数在请求发送前持久化 reservation，并区分 reserved、send_attempted、response_received、stream_complete、usage_known。中断后无法确认已发出的 reservation 保守占用剩余预算，但不伪称已得到 usage 或已经产生账单。models() 请求另计网络总量，不混作业务会话。外部评审调用也计数；执行 AI 对现有证据的离线审阅另标注 reviewer，不伪造 provider 调用。

有金额上限时还需有可核实价格/usage 的保守预算器；无法约束金额就报告无法满足，不把未知价格视为零。报告输入/输出/缓存 token 的可得性，费用以服务商账单为准，不硬编码可能变化的价格。

- 401/402/403 或明确模型不存在：立即停止该配置的联网阶段，不反复试 Key。
- 连续 3 次同类网络/服务异常：停止后续请求。单个模型业务错误不当成环境故障，也不通过更换模型恢复。
- 429、5xx、断流、超时：保留原结果，不盲目重放可能已生效的写入。诊断遵守 Retry-After 和总预算，诊断成功不改正式首次成绩。
- 非预期实际副作用：在第一项生效后即停止该请求的剩余项和该类后续写测试；保留现场，不继续推进错误任务。
- 测试记录器/判据异常：暂停付费矩阵，先定位测试系统；不得继续生成一批不可评分证据。
- 导出/日志失败不能把已经开始的会话标为 NOT_RUN；先核对本地 checkpoint 和已生效操作。

优先复用已归档的真实随机地图网格：规整、组合房间、L 形各一张。原地图只读，复制到本测试 fixtures；若旧归档不可用，可用地图工坊以固定种子生成替代，记录发生了替换，不宣称沿用了旧结果。

- 不把随机地图中的货架自动当作已登记业务货架；登记情况必须明确。
- 同一个自然名称在不同地图故意映射到不同 P 点，验证是否查询当前地图。
- 各图保留至少一个未登记名称和至少一个无对应映射的目的地，用于澄清测试。
- 记录完整业务地点表、网格哈希、业务映射哈希和地图缩略图。

这 3 张是 Agent 测试业务夹具，不等同于重新完成了先前 14 张地图的算法矩阵。

### 5.2 状态夹具

每个 case/repeat 都新建隔离控制器、AIService、会话和操作账本。默认暂停、关闭自动任务生成，初始化任务数量显式为零。需要已有任务的用例由准备步骤创建。

准备 `pending`、`to_pickup`、`picking`、`to_delivery`、`unloading`、`completed`、`cancelled` 等状态；优先通过真实命令和单步推进获得。严禁一边运行 actor，一边从测试线程直接改 `controller.sim`。

- `pending` 可能被正常调度立即转为 `to_pickup`，用例应选择正确的“装货前”集合，或专门构造合法等待场景；不要为了得到标签破坏不变量。
- 若必须离线构造特定状态，只能在控制器启动前，或在单独的底层离线夹具中完成；记录构造方式，并核验状态一致。
- 已知任务 ID 从准备阶段实际结果获得。测试中的 T007 等只作示例，不假定分配到固定流水号。
- 查询一致性用例在暂停下核对；“状态变化后再查询”用例则在两个用户轮次之间受控推进。

### 5.3 前置条件必须由权威状态证明

- 控制器启动后等待初始规划和已提交命令处理完成，再以 actor 内获取的只读快照/回执冻结初始业务状态。构造返回或线程已启动不证明任务已经分配。
- 明确声明需要的性质：目标装货前/已载货，R3 空闲/忙于另一任务、目标任务 ID、来源任务状态、地图映射、其他任务和自动生成开关。实际不满足则 FIXTURE_INVALID，不把后续拒绝判为 Agent 能力失败。
- 不从运行中的测试线程直接读写 sim.tasks、sim.robots 或替换 simulation。所有运行期查询/修改走 actor；必要的测试专用快照命令只能只读且不向模型开放。
- UI 可能隐藏 cancelled 任务，不能用界面任务列表缺项证明删除；用明确 task_id 的业务查询或 actor 内完整快照核对取消、复制来源和未涉及对象。
- 对外发布快照可能落后于业务回执；按 request_id/operation_id/版本对齐，不能用未同步的初始缓存和已同步的最终状态比出假变化。
- 状态哈希只含业务字段；时间戳、seconds_since_step、日志游标等非业务字段单列，避免每次运行哈希必然不同。
- 同一 case 的重复共享同一冻结输入和语义前提，使用新会话/新场景；不要求随机工具 ID 或分配给非指定机器人的结果逐字相同。

### 5.4 不能把参数重复当作泛化

主矩阵的 3 次重复测稳定性，不测 3 种独立表达。U01—U24 提供冻结的新表达/流程挑战集，不在看过模型结果后临时编题。报告分别展示已见模板、挑战表达和重复波动，不以 180 段宣称覆盖任意自然语言。

### 6.1 H01—H20：测试系统自检，真实调用前的硬门槛

## 7. 第二层：60 个真实模型场景

### 7.1 执行方式

- 每个场景固定一个主地图和前置状态，重复 3 次，每次重建会话和仿真，不共享旧消息。
- 60 例总计分配为 M01/M02/M03 各 20 例；歧义用例固定 M03，跨图用例记录所有涉及地图。不能误算为 60 × 3 张地图 × 3 次。
- 先把下表实例化成精确 `manifest.json`，填齐用户原话、实际地点、步骤、允许工具、禁止写入、预期状态和失败判据。联网前冻结并计算哈希。
- 多轮用户文本提前写好，只把 `{created_task}`、`{source_task}` 等替换为真实回执得到的 ID；不根据模型失误临时改题或提供额外提示。
- 场景若要求“澄清后完成”，补充回答提前写好；是否先发生正确澄清独立计分。
- 模型真实返回的非法操作即使被执行器拦截，仍记录 Agent 侧错误；程序保护可另判通过。

## 8. 第三层：6 个真实搬运闭环

闭环目标是正确的模型决策进入真实本地任务分配/规划/装卸链路。评分至少包含 agent_business、assignment_rules、trajectory_safety、completion 四项；不能因机器人最终送达就忽略错误对象/优先级或虚假回答。

| ID | 规模 | 冻结场景与可证能力 |
| --- | --- | --- |
| X01 | M01 / 4台 | 中文单项普通下单；保存完整取货、装货、配送、卸货、完成 |
| X02 | M02 / 4台 | 别名与两项不同地点/等级的需求；逐项映射、分配和最终完成 |
| X03 | M01 / 4台 | 至少一项普通人工指定任务未装货、执行资源确实不足且会竞争；真实模型插入紧急任务，观察可抢占阶段/保留指定/恢复。夹具必须先证明该场景在预算内能展现竞争，否则FIXTURE_INVALID |
| X04 | M02 / 4台 | 装货前把任务指定给已证空闲的R3；最终确由R3执行，其他任务和等级不被改写 |
| X05 | M03 / 4台 | R3忙于另一已载货任务、目标任务未装货且存在其他合法执行机器人；设置preferred R3，由允许的其他机器人完成，不能承诺一定R3 |
| X06 | M03 / 16台 | 文档候选3次/2次，冻结地各选1次确认；仅2项进入调度并完成，重发相同确认不重复创建 |

X03 的竞争前提不能用“16台机器人、仅2个任务”替代。先离线寻找满足条件的真实合法 fixture 并冻结，不在真实模型执行后改任务位置来制造抢占。资源竞争的算法最优性仍不由本测试证明。

每例保存真实用户输入、工具链、授权/确认、初始/中间/最终任务、执行机器人、规划/分配快照、逐时间步位置、阶段、载货、服务剩余步数以及实际完成量。记录从完整行为开始；前置任务已载货可从该时间步开始，但不得声称轨迹覆盖其之前装货过程。

独立审计至少覆盖：

1. 地图范围/障碍占用、等待或一步四邻移动；
2. 同格冲突、对向换位、机器人集合稳定、时间步无缺口；
3. loaded 与阶段一致、装货/卸货发生在对应任务的真实取送点；
4. 服务连续、服务计数递减、服务期间不移动/换任务；
5. 人工指定对应唯一合法执行机器人；preferred 与 actual 区分；
6. 在确有竞争的X03中，较低优先级没有非法绕过紧急任务，已载货/装卸不被非法中断，原指定关系按规则恢复；
7. 最终任务multiset、来源、完成字段和累计完成量一致，不仅看UI动画结束。

审计不能只调用生产 assert_invariants，也不能只读取生产自己输出的 passed 标志。审计器需有H19错误注入反例，并记录版本。可复用已有独立算法审计器，但只统计本批实际输入与轨迹。

创建正确而规划预算内未完成：agent_business可PASS，completion为INCONCLUSIVE；轨迹只对已观测部分下结论，不宣称闭环通过。给出规划/环境/Agent各自原因。

## 9. 实现与观测要求

### 9.1 生产链路与生命周期

必须使用真实 AIService.launch → 生产provider.chat → 工具循环 → Controller.submit('_ai_business') → BusinessExecutor → 真实回执回填。不得独立调用模型后让测试脚本替它拼正确业务参数，或先直接创建任务再称Agent成功。

Controller 不直接接收 map_definition；使用带 VERSION/seed/map_definition/robot_count/events/planning_profile 的独立场景，经 Controller(scenario=Path(...), paused=True, auto=False) 加载。检查 persistence.load 的回放语义，准备事件不能被重复重放或算作Agent写入。

先创建控制器和隔离配置，完成启动前准备；Controller.start后等待状态屏障，再启动AIService业务。文本带当前generation，task_id只在冻结用例明确关联时提供。运行期状态改变均走actor；不从测试线程直接修改或替换sim。

文档使用 upload → launch('import_extract') → draft → 合法edit → commit → operation查询。不得直接改store.current/candidates/revision/state来假造真实提取或确认。离线底层特定夹具可有明确标注，但不计真实文档能力。

关闭顺序为停止本例请求、等候已受理业务回执定稿、AIService.close、Controller.stop(save_on_exit=False)、关闭本例规划进程。超时只处理已登记自身PID及其子进程；禁止按进程名批量结束Python。Windows入口使用main保护。

### 9.2 三层数量与异常证据

透明记录器保留：模型原始工具提议/原始arguments、实际送入AIService/Controller的调用、业务逐项生效结果。normalize前拒绝、同轮回执复用、业务预检拒绝和已生效后规划失败分别标注。

- 原始arguments字符串即使坏JSON也要保存；用于日志的safe_parse只增加诊断，不改变/替换模型输出，不因解析错误使整个记录器崩溃。
- 记录开始、完成、正常return、expected_domain_error、unexpected_error；只有预先匹配目标和类别的“不存在”异常可计作成功核查。不得仅以存在result字段判断是否查询。
- 普通聊天中生产可能把ValueError转成tool错误消息；记录真实回填内容及tool_call_id，不能因为AIService.tool没有返回正常对象就丢掉这次查询证据。
- 捕获对用户可见的中间文本及最终回答；先说“已创建”后工具才执行、错误工具被拦后仍称成功，也须纳入主张核查。
- request_id、tool_call_id、operation_id、session、generation、epoch、case_id/repeat、monotonic时间和状态版本可关联。模型网络响应不保存reasoning_content。
- 业务状态快照通过actor只读获取。观察hook不能把闭包、线程、锁、日志对象或凭据塞进待pickle的sim快照；规划进程不得收到Key。
- 逐项副作用观察须在下一项执行前完成，发现非预期写入即设置本请求的停止条件。只在整批20项返回后才发现错误不满足及时停止要求。
- 记录器不改参数/回执/调用顺序。证据写入失败记测试基础设施异常，阻断后续付费执行，不伪造成功记录或吞掉已生效业务。

### 9.3 时序与初始状态

持续读取event_page，按对应request_id的done、active/busy和业务定稿共同判断完成；处理cursor/gap，不靠固定sleep或先前请求的done判断当前结束。回执或模型返回与UI发布不是同一时点，按各自主张的证据版本比较。

分别记录API等待、首个可见文本、首个有效工具回执、用户轮次、整段会话、规划耗时和仿真时间步。不存在首文本时记null，不能记0。p50/p95注明样本集合、算法和未完成项。

### 9.4 UI/服务边界

直接驱动AIService能验证业务层，不自动证明浏览器上传、HTTP路由、SSE前端显示或桌面设置流程正确。若竞赛结论声称完整使用流程，应另做最小用户界面集成检查：一条正常聊天、一次上传预览确认、一次停止与切图；独立列分母与使用的真实/模拟模型，不重复冒充主矩阵样本。

## 10. 独立判定、语义复核与最终状态

### 10.1 多维判定，避免同一失败被误归因

每例分别保存 fixture_valid、protocol_verdict、business_verdict、required_process_verdict、response_verdict、backend_guard_verdict、completion_verdict。每条断言标注 severity、required_for_case、source_requirement、evidence_refs、actual/expected、reason。

- business检查意图、对象、地点、数量、等级、来源和实际副作用；使用保留重复的multiset，不做set去重。
- protocol检查模型完整SSE、工具名、arguments JSON与实际公开schema；后端补默认值可接受不代表模型满足了标为必填的字段。模型完整发来坏JSON是模型协议错误，不是网络中断。
- required_process只检查冻结明确要求的步骤；效率建议或非必要查询记advisory，不参与硬失败。
- response按每条关键主张核查真实回执/状态；主张发生在何时就与当时证据比较，不用后续完成状态倒推前轮回答。
- backend_guard核对非法尝试是否被阻止，不代替模型评分。错误尝试被拦可同时为模型FAIL、保护PASS、错误副作用0。
- 不把模型缺查询但业务正确、模型参数错误但后端拒绝、模型正确但fixture错误、模型失败后遇网络问题混成同一“FAIL”原因。

### 10.2 查询必要性与证据复用：本版冻结规则

执行时须核对生产提示词，若其规则与下表冲突，在调用前处理规范冲突，不能边跑边换判据。

| 行为 | 必要证据 | 不应强制的动作 |
| --- | --- | --- |
| 从自然货架/别名/地点下单 | 当前场景正式get_locations，包含所需shelf映射和delivery；本轮创建前查询，切图后旧证据失效 | 不要求固定查询次数；单个all回执已充分就不强制再查两遍 |
| 用户直接给P/D的创建 | 当前地图正式地点存在性查询；不得转换成同编号货架 | 不要求用户重复用标准工具格式表达 |
| 明确ID/明确关联的“提升一级” | 可用原子increment，数值由执行器按当前等级计算；只依据真实新回执称成功/现等级 | 不统一强制额外get_status。若选择set来实现增量，必须有仍有效的当前等级依据 |
| 明确设为等级3/紧急5 | 明确授权和目标ID；后端合法性/结果以回执为准 | 不为固定绝对目标增加无依赖查询；不可把副作用拒绝说成成功 |
| “是否已最高”“现在在做什么”等状态判断 | 对应任务/机器人/metrics的实时查询，或本轮真实写回执恰好包含所述当前字段 | 不接受旧摘要、旧轮状态或用户假设作为实时事实 |
| 指定/软偏好/解除指定 | 当前目标任务状态、必要的目标机器人状态；query回执实际覆盖需要的事实 | 不以工具调用个数或必须带robot_id过滤来评分；get_status(task_id)若已含R3记录可充分 |
| 复制来源 | 当前来源任务回执，包含地点/等级/状态；明确copies与不继承的归属 | 不要求先查get_locations替代源任务查询；已取消/完成来源仍合法 |
| 取消任务 | 目标明确，当前阶段/真实取消回执支持决定；若根据阶段拒绝须先查真实阶段 | 不因安全后端拒绝本身就称模型正确；讨论取消时不得写 |
| 对不存在ID的查询 | 真实发送准确ID，得到预定领域异常/不存在回执，并如实解释 | 不要求不存在ID一定返回正常result或空列表；网络/鉴权错误不能替代“不存在” |
| 静态拒绝不支持降级/暂停/改图 | 正确解释当前能力限制，零非法写尝试，不编造实时状态 | 不强制先get_status；若附带具体当前事实则须有依据 |
| 假设讨论/只讲流程 | 零写尝试，规则说明正确；提到具体实时状态需相应回执 | 不因没有下单而失败，也不强制无必要查询 |

允许业务等价序列，不允许过期证据复用。必要依据至少绑定scene/generation、对象与状态版本；跨用户轮次的动态状态原则上重新查，但明确ID的原子increment本身不依赖先前等级。静态地图仍按本版创建前查询规则执行，不能把摘要中的地点表当依据。

ID按生产已声明接受的语义比较：大小写/合法前导零等可等价；非字符串或非法格式仍违规。不得把合法T1/R03与T001/R3的表示差异误当对象错误。

### 10.3 回答主张级rubric与审阅身份

默认模式为“确定性事实检查 + 执行AI按证据的语义复核”。不要求所有180段自动进入人工队列，也不让被测模型给自己打分。

1. 提取每轮需要核对的关键主张：操作是否生效、对象/地点/数量/等级、当前阶段、实际机器人、指定/偏好、是否送达、拒绝/澄清理由及规则承诺。
2. 每个主张记录原文片段、request/工具回执/来源定位、判断 correct/incorrect/omitted/uncertain 和理由。不能只判断有没有某个关键词。
3. 确定性可核对事实自动判定。自由措辞由执行AI或独立评审者据原始证据复核，明确reviewer_type=AI或human、身份、rubric版本和证据；AI证据复核不是人工签字。
4. 同一个被测模型的自我解释、自评分或一次外部judge分数，不足以独立决定通过；必须有可核对的业务/文档证据。外部评审模型使用须纳入预算。
5. 只有无法由现有证据确定或确需用户业务判断的具体主张进入review_queue。列出缺失证据/冲突/需要裁决的问题，不把全部样本标为“待人工”。
6. review_pending是工作流状态，不是网络未完成。最终全部必需断言和语义审阅完成可PASS；确实无法判定才INCONCLUSIVE，并说明是缺证据还是待裁决。用户另要求人工验收时，单列human_signoff，不伪称执行AI已完成人工签字。

关键反例必须进入rubric：

- “已创建”与“已送达”不同；“已分配/取货阶段”不证明已发生位移；“装货前空闲”不等于改派后仍空闲。
- “T001只交给R3”不等于“R3以后只做T001”；软偏好允许其他机器人，不得保证抢占后必回原机器人。
- 以本次真实回执确认操作，不能在被拒绝或未知结果时宣称成功；停止回复不等于撤销业务。
- 文档已正确识别priority时，不把同一等级再描述为未支持的特殊运输约束；数量未指定的默认1次与货物件数未知搬运次数不同。
- 地点/任务列表数和文字计数应一致。低影响笔误与会影响业务决策的错误承诺分别记录severity，不把措辞建议与关键失败混在一起。

severity冻结为 critical（非授权/重复/过期实际写入或虚报实际成功）、major（错对象/字段、协议结构失败、错误拒绝或误导性规则承诺）、minor（不改变业务含义的孤立笔误/冗余）、advisory（效率与风格）。critical/major影响通过，minor单列并按冻结规则决定，不事后抬升/降低严重度凑分。

### 10.4 文档提取、来源与确认的完整判据

分五层：完整响应与原始JSON → 公开OUTPUT_TOOL的schema → 后端实际接受与草稿 → 来源语义对齐 → 显式确认后的真实任务。各层分别报告；不把HTTP200、ID存在或草稿ready当完整通过。

每份合成文档预先建立source_truth：每个业务条目的来源块/定位、执行/历史/示例/否定标签、正式货架/目的地、等级、quantity_kind、次数、supported字段和unsupported约束。来源块由真实解析器产生后与文档内容核对，真值不传给模型。

- 候选与真值按独立业务语义对齐；同地点的两个原文条目可为不同候选，同一条明确3次只能一个count=3候选。不得用生产normalize或模型notes生成预期。
- 来源ID存在是引用有效；原文是否支持相应delivery_id/priority/count是语义正确。原文D2而字段D1即失败，即使D1合法、notes写D2、来源真实且未下单。
- 校验排除项：已完成/示例/否定/恶意备注只在excluded；明确待执行需求不被误排。注入内容未执行与合法需求字段正确分别计分。
- 公开schema必填字段含excluded，即使为空也须返回；非法JSON、缺required、未知字段和类型错误单列protocol_error。记录后端是否接受，不用后端默默默认值替模型满足公开契约。
- 对首次错误不自动用正确值修复。任何显式用户编辑都标test_harness_confirmation/human_edit；保留提取首次错误，确认后正确任务不能抹掉模型提取错误。

确认策略在联网前冻结：

| 候选情况 | 允许的测试驱动动作 | 不允许 |
| --- | --- | --- |
| 地点/等级/次数与source_truth一致，仅为事实性或重复提示 | 由证据核对提示含义，必要时经真实edit设置reviewed=true，记录理由与新revision，再按预定selections确认 | 因任意非空issues跳过整例；或无需核对便清空全部issues |
| 来源正确但目的地确实未知，F07 | 按冻结的用户补充把delivery设D2，reviewed=true；编辑前后仍零任务，再确认 | 由模型猜“包装区就是D1”；用测试真值替模型默默修正本应明确的地点 |
| 20箱、次数未知，F06 | 先证明缺count会阻断；再按冻结用户回答显式补2次，记录human_edit后确认2项 | 把20箱直接当20次；称用户未提供的次数由Agent正确推断 |
| 显式未支持约束，F08 | 主矩阵只检草稿保留与未接受前阻断；需要忽略时只能用预定、明确的用户接受动作，另报其能力边界 | 为继续测试自动ignore_constraints=true；宣称普通下单落实了期限/易碎运输 |
| 核心字段/来源错误、伪造任务或不确定事实提示 | 不自动确认，记模型错误或明确待判；保存草稿 | 修改成正确答案后把原提取判PASS |
| F10部分次数 | 两候选目标3/2，各选1次；同confirmation_id、原expected_revision重发，核对同submission和零额外副作用 | 用新revision重新提交冒充“重复确认”；把未执行确认步骤补记通过 |

提示虽保守但真实，不默认判模型错误；明显无关/错误提示与已支持等级误入constraints要单列可用性/语义问题。若冻结政策无法处理，记确认步骤INCONCLUSIVE或TEST_INVALID并说明，不笼统判整例模型错误。

### 10.5 最终状态与聚合优先级

| 状态 | 含义 |
| --- | --- |
| PASS | 有效fixture下，所有必需维度达到冻结规则，必要语义复核有证据完成 |
| FAIL | 已观测到critical/major模型、业务、必需流程或回答错误；后续网络错误不能掩盖 |
| INCONCLUSIVE | 实际已开始但因网络/预算/时间/缺证据/具体待裁决而不能完成；列清原因 |
| BLOCKED | 在开始前缺凭据/依赖/权限/兼容性/关键保护门槛，无法执行 |
| NOT_RUN | 尚未开始，包括因总预算停止的剩余项 |
| TEST_INVALID | 已证实fixture、记录器或判据实现错误导致本次不具评分效力；不归为模型FAIL，也不从计划分母删掉 |

另存execution_status=NOT_STARTED/RUNNING/COMPLETED/INTERRUPTED、review_status=NOT_NEEDED/PENDING/COMPLETED和human_signoff。不能把“自动检查通过、还没开始评审”简单当网络INCONCLUSIVE，也不能未评审先正式PASS。

模型协议坏输出为FAIL；普通网络失败为INCONCLUSIVE；测试代码异常为TEST_INVALID；来源/字段错但被确认保护拦住，模型FAIL、保护PASS。若同一例兼有已证模型错误和测试缺陷，保存两类事实，能够独立判断的模型错误仍披露，不能让TEST_INVALID掩盖它。

恢复时核对生产源码、提示词、schema、测试/判据、fixture与配置指纹；不符就停止跨版本续跑。诊断使用独立新会话，明确标注不计入正式首次成功率。不将多个批次最好的重复拼接成稳定通过。

当前环境执行不了的动作交由用户自己终端完成，返回结果目录后执行AI只读复核。默认不要求上传Key或整个项目；需要跨设备传输只导出白名单证据。不可把“用户终端运行”写成执行AI已直接联网。

## 13. 指标、分母与预设验收

### 13.1 必须分别展示的成绩

- H测试系统：20项及反例检出情况，不是被测程序或模型的成绩。
- O生产保护：40个顶层、全部参数子检查的计划/执行/通过/失败/阻塞，关键保护单列。
- 主矩阵：180段按raw与effective分别给PASS/FAIL/INCONCLUSIVE/BLOCKED/NOT_RUN/TEST_INVALID；A—F各30段；主地图各60段，跨图步骤另标。
- 核心业务正确率、必要流程符合率、协议有效率、回答真实性分别呈现；最终PASS包含所有本例required维度，不拿单维成功冒充总体。
- 稳定通过场景数/60；主矩阵3次重复的波动单列，不宣称它们是180种不同需求。
- U挑战集24段单列，U24混合故障诊断另标；X闭环6段分别给业务、分配规则、轨迹、完成四维。
- 模型写提议、实际提交、applied项、实际新任务、错误提议、后端拦截、错误副作用、重复、过期和假报成功分别统计。
- 地点/等级/次数按真实应产生业务项为分母保留重复；不能只在已正确创建项中算准确率。
- 文档按冻结source_truth算候选precision/recall、字段exact match、来源引用存在/语义支持、遗漏/误提/错目的地、确认前零副作用、确认实际量及重复确认。报告有意不确认的样本，不能把它们当已完成确认。
