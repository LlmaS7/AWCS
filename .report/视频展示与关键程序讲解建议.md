### 3.2 第一屏：任务等级如何进入目标

以下为 `match` 第 19～34 行源码节选（含中文注释）：

```python
for task in tasks:
    eta = cost(slot, task)
    # 不符合人工指定等约束的关系不可选，不能用距离优势抵消业务约束。
    if eta is None or eta >= 10**6:
        row.append(None)
        continue
    if not isinstance(eta, int):
        raise ValueError('Matching ETA must be an integer number of ticks')
    value = [0] * dimensions
    # 求解目标取最小值；某级每多分配一项，该级计数减一。
    value[5-task.priority] = -1
    # 各级分配数量相同后，再比较偏好，最后比较 ETA 和创建时刻。
    if preference:
        value[5] = preference(slot, task)
    value[-2:] = [eta, task.created_at]
    row.append(tuple(value))
```

这段代码建议标注三处：

- `value[5-task.priority] = -1`：为 5、4、3、2、1 级分别设置目标维度。由于求解取最小值，某一级分配数量越多，该维度越小。
- `preference(slot, task)`：在前面的等级目标相同后，再考虑可以立即接手的机器人偏好。
- `value[-2:]`：之后比较预计完成代价与任务创建时刻。创建时刻作为末级代价，不能据此声称严格的逐项 FIFO。

`None` 表示当前匹配关系不可用，例如不符合人工指定；程序会在求解矩阵中将其转换为不可选代价。

### 3.3 第二屏：如何保证紧急程度不会被距离覆盖

以下为 `match` 第 40～53 行源码节选（含中文注释）：

```python
ranges = [sum(max(v[d] for v in row if v is not None)-low[d]
              for row, low in zip(vectors, lows)) for d in range(dimensions)]
# 从低位向高位构造权重，保证高位改善一单位能压过全部低位变化。
# 因此长距离不会挤掉高等级任务，无需人为猜测固定优先级系数。
weights = [1] * dimensions
for d in range(dimensions-2, -1, -1):
    weights[d] = weights[d+1] * (ranges[d+1]+1)
encode = lambda v, low: sum((a-b)*w for a,b,w in zip(v,low,weights))
finite = [[None if v is None else encode(v,low) for v in row]
          for row,low in zip(vectors,lows)]
# 禁用代价高于任意全可行匹配的总代价；空分配列保证始终有可行选择。
forbidden = 1 + sum(max(c for c in row if c is not None) for row in finite)
# 匈牙利算法求整个矩阵的匹配；最优性仅针对本轮给定约束和代价。
columns = minimum_assignment([[forbidden if c is None else c for c in row] for row in finite])
```

建议解释：先计算各目标的取值范围，再从低优先级目标向高优先级目标构造权重，使高位的一单位改善能够压过全部低位变化。随后调用匈牙利算法，得到机器人与任务的整体匹配。

这是本段最值得讲的设计：**优先级是有顺序的目标，而不是随意给“紧急任务”加一个固定分数。** 每行还加入空分配列，允许机器人暂时不接任务。

预计完成代价的基本组成是：

```text
机器人可释放时间 + 到取货点的网格最短距离 + 装货时间
                 + 取货点到配送点的网格最短距离 + 卸货时间
```

这是给定模型下的估计值；默认不包含之后协调路线产生的全部避让等待，也不预测未来插单。

### 3.4 用一个小例子解释“整体匹配”的价值

以下为教学用假设矩阵，所有任务同等级、无人工指定与软偏好，不是项目实测数据：

| 预计代价 | 任务 A | 任务 B |
| --- | ---: | ---: |
| 机器人 1 | 1 | 2 |
| 机器人 2 | 3 | 100 |

如果先把 A 贪心地交给机器人 1，再将 B 交给机器人 2，总代价为 101；整体匹配可选择“机器人 2 接 A、机器人 1 接 B”，总代价为 5。

口头讲到这里即可，无需逐行推导匈牙利算法。

### 3.5 可直接使用的讲解词

> 任务分配需要同时考虑业务紧急程度和机器人状态。这里先把任务等级编码成分层目标，保证高等级任务的分配数量优先；在这些目标相同后，再考虑机器人偏好和预计完成代价。随后使用匈牙利算法进行整体匹配。实际调度还分为紧急任务与剩余任务两个阶段：已经载货或正在装卸的机器人会先完成当前作业，必要时预约后续紧急任务。

### 4.2 第一屏：已经规划的路线如何约束后续机器人

以下为 `Reservations.add_path` 第 42～54 行源码节选（含中文注释）：

```python
def add_path(self, path, persistent=True):
    # 将连续停留合并成闭区间预约，移动与等待都会占用格子。
    begin = 0
    for t in range(1,len(path)+1):
        if t == len(path) or path[t] != path[begin]:
            self.block(path[begin],begin,t-1)
            begin = t
        if t < len(path) and path[t-1] != path[t]:
            # 本车在 t 时刻从 A 到 B，禁止后车同一步从 B 到 A，避免对向换位。
            self.block_edge(path[t],path[t-1],t,t)
    # 到达停车终点后仍占据该格，不能把已完成路线的机器人视为消失。
    if persistent:
        self.block(path[-1],len(path)-1,INF)
```

可配两个很小的示意：

```text
同格冲突：在 t=4，R1 与 R2 都占据格子 X。
对向换位：从 t=4 到 t=5，R1 从 A 到 B，R2 从 B 到 A。
```

对应解释：

- `self.block(...)`：登记某个位置被占用的时间区间，后续机器人需避开。
- `self.block_edge(path[t], path[t-1], t, t)`：已规划机器人从 A 到 B 时，禁止另一机器人同一步从 B 到 A。
- `self.block(path[-1], ..., INF)`：到达停车终点后继续占据该格，不能假设机器人抵达后会消失。

### 4.3 第二屏：SIPP 如何选择安全的到达时刻

以下为 `search` 第 103～117 行源码节选（含中文注释）：

```python
for q in warehouse.neighbors(p):
    for j,(a,b) in enumerate(reservations.safe_intervals(q,horizon)):
        # 最早下一步到达邻格；若邻格尚不可用，则在当前格等待后再出发。
        arrival = max(t+1,a)
        if arrival>b or arrival-1>end:
            continue
        # 前面的条件同时检查邻格到达时刻和当前格等待期限，再避开反向边冲突。
        arrival = reservations.next_edge_time(p,q,arrival)
        if arrival>b or arrival-1>end:
            continue
        # 边冲突可能推迟到达，需再次检查区间，并确认装卸停留能否完整执行。
        normal = normalize(q,arrival,k,done,b)
        if normal is None:
            continue
        nt,nk,nd,_ = normal
```

推荐只讲四点：

1. 取邻格 `q` 可用的安全时间区间 `[a, b]`。
2. `arrival = max(t+1, a)`：最早下一步到达；若邻格还不可用，则推迟出发。
3. `arrival-1 > end`：如果等待会超出当前位置的安全区间，这条转移不可用。
4. 再检查反向边冲突和到达后的装卸停留是否能完整放进安全区间。

例如：在规划范围 0～10 内，某格被占用的时间为 3～5，则安全区间为 0～2 和 6～10。机器人可调整到达时间，而不仅仅是寻找另一条空间路线。

SIPP 用位置、安全区间等信息组织搜索；本实现还记录下一作业点与已完成交付代价，以处理取送顺序和连续装卸。不要把状态仅解释为一个坐标。

### 4.4 补一句系统层面的协调策略

在默认 16 台演示配置中，主体是依次执行安全区间搜索并累积预约。某种规划顺序失败时，程序尝试调整顺序；符合触发条件且预算允许时，对少量相关机器人做局部 CBS 修复。并非每次规划都会用到局部修复。

当前默认协调器对不超过 8 台的完整路径场景还可能先尝试短预算 CBS。因此，若讲默认多机器人方案，建议沿用 16 台演示，并核对调试窗口显示的实际算法。

### 4.5 可直接使用的讲解词

> 多机器人可以各自拥有一条空间上很短的路线，但它们可能在同一时刻到达同一位置，或者在相邻格之间对向换位。因此我们把路线放到时间维度上协调。这里先将已规划路线写入预约表，后续机器人在安全时间区间中搜索，并在需要时等待。系统还会调整规划顺序、尝试局部冲突修复，最后独立校验整组路线，只有通过检查的方案才会提交执行。

### 5.3 用一次真实交互展示闭环


工具次序和次数以实际请求与模型响应为准。模型可以复用有效上下文，不能把某段预设调用顺序描述成每次都一定发生。

若视频还有余量，再补一条信息不完整的需求，展示助手如何请求补充地点；或展示已装货任务无法取消的真实拒绝回执。录制操作前核对任务实际阶段。

### 5.4 可直接使用的讲解词

> Agent 为用户提供自然语言业务入口。模型先通过工具取得当前地图和任务信息，再把需求转换为结构化操作。这里的循环会把真实工具结果回填给模型，使它能够继续处理和解释结果。执行前还有参数、业务状态和场景有效性检查。最终任务分配与机器人路线由本地调度模块完成，模型根据程序回执报告结果。

### 5.5 值得补充的工程设计

- **受限能力**：提供十类业务工具；暂停、切图和完整路线生成由对应程序模块处理。
- **结构化与状态校验**：工具参数经过 `normalize`，动作进入业务执行器再次检查，不能只依赖提示词维持规则。
- **重复调用处理**：同轮相同写操作有结果复用，执行器对相同操作标识核对指纹并返回记录结果。范围是当前运行与对应记录，不是跨重启的永久去重。
- **结果分层**：任务操作已生效与路线是否可执行分别返回；已经创建任务后，规划失败不会自动回滚该任务。
- **调用上限**：当前 `_chat` 最多 8 轮模型调用、12 次工具调用，避免一次请求无限循环。

这是一个带工具调用和业务约束的仓储助手。机器人数量增加不代表启动了同等数量的大模型 Agent；视频中应分别说明业务助手与多机器人规划的职责。

## 六、录制前的准备与画面安排

### 场景准备

建议从下面的暂停场景开始，打开主窗口和调试窗口：

```powershell
.\.venv\Scripts\python.exe main.py --map fleet_64x64 --robots 16 --paused --debug-window
```

基础展示建议使用 `scalable_full`，任务—路径联动先设为 `off`。如果要额外讲有限候选联合评估，再显式切换 `candidate`，同时说明这是有限候选集内的改进。

录制前排练两段画面：一段能观察到取货前的紧急插单或后续预约；一段能观察到共享通道中的等待与通行。固定地图、数量、随机种子、任务顺序和规划预算，记录成功的演示条件。相同种子不能消除时间预算与机器性能带来的差异。

### 代码画面

- 编辑器放大到 1080p 视频能直接阅读的字号，显示函数名与行号。
- 每屏约 10～20 行，预先折叠无关函数；工具定义较长时仅展示相关字段。
- 每段先用一句话说清问题，再标注代码中的关键条件，随后切回对应运行结果。
- 代码节选保留真实文件位置；为了讲解写的简化示意应标注“伪代码”或“示意”，与原始实现区分。

### 演示结果

完成任务数、平均完成时间、距离和等待步数足以支撑主线。平均完成时间使用调度时间步，距离使用网格单位；不要把它们直接说成现实秒数或米数。

展示某段等待时应说明观察范围；“这次演示通过了路径校验”不能扩大为“任何情况都不会死锁”。如需声称性能提升，应提供同地图、同任务、同配置下的对照实验，当前稿中的教学矩阵不构成性能证据。

## 七、如果评审继续追问

| 问题 | 建议回答 |
| --- | --- |
| 为什么不直接按最近机器人分配？ | 单次最近选择可能增加整体代价。项目将当前候选关系形成矩阵，并在分层目标下做整体匹配。 |
| 为什么 SIPP 适合这里？ | 已规划路线能形成占用时间区间，SIPP 在安全区间内选择转移时机，适合表达等待与通行约束；效果仍需结合具体场景测量。 |
| 任务分配与路径是联合求解吗？ | 默认是给定代价下匹配，再做路径协调；可选拥堵估计或有限候选路径评估，均不声称完整全局联合最优。 |
| AI 会不会把错误指令直接交给机器人？ | 工具请求先经过参数与业务规则校验，调度和路线由本地程序计算，模型依据实际回执报告结果；模型理解仍可能出错，需要核对。 |
| 这是自己的原创算法吗？ | 基于匈牙利算法、SIPP、CBS 等成熟方法进行项目内实现与场景适配，重点在业务建模、模块协同和可视化系统；研究来源见 `THIRD_PARTY.md`。 |
| 能控制真实机器人吗？ | 当前交付是静态网格下的仓储协同仿真，实体机器人接口与真实动力学尚未实现。 |

## 八、最值得保留的收尾讲法

> AWCS 将自然语言业务交互、任务分配和多机器人路径协调连接到同一个仿真流程。用户可以提出搬运需求，程序根据业务优先级选择执行者，再通过时空约束协调通行，最后在界面与指标中观察执行结果。当前重点是验证这套流程的可用性，后续可继续开展更系统的性能评测与实体接口扩展。
